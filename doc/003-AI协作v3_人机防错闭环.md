# 003 · AI 协作 v3：人机防错闭环

> 版本：模板 v3.0 ｜ 日期：2026-10-18 ｜ 关系：在 v2.6「七门闸门」之上补**闭环**，不推翻既有约定
> 读者：项目负责人（判断）＋ AI（执行）＋ 未来的接手者（追溯）
> 一句话：**v2.6 让机器能判定「做完没有」，v3.0 让机器同时回答「现在什么情况、AI 改了什么、失败了先做什么」。**

---

## 1 审计：v2.6 已经很强，但缺三个接口

逐文件读了模板的 6 个入口文件、`tools/` 下 11 个脚本与钩子、`xz-inspector` 的 `tests/run_all.sh`，结论是：
**闸门（判定）做得比「接口（人机交接）」好。** 判定已经有了，但判定结果没人接得住。

| # | 现状 | 缺口 | 真实后果 |
|---|---|---|---|
| D1 | `run.sh` 输出中文文本，只给人看 | 无结构化结果；CI/AI/看板只能 `grep` 中文措辞 | 改一句文案，下游全崩；AI 无法可靠判断「哪门红了」 |
| D2 | AI 每会话读 6 个入口文件（约 13KB，实例化后更多） | 没有「状态压缩」层；读得越多越容易漏掉最关键的 3 行 | 跨会话恢复靠重读，token 贵且注意力散 |
| D3 | `STATE.md` 要人手写，`--status` 只给 4 行草稿 | 状态与实际（git / 闸门 / 基线 / 用例）不同步 | 「文档说能跑，实际没基线」这类假状态 |
| D4 | 闸门只在**提交那一刻**跑 | 编辑期没有任何反馈；夜间失败无人接 | 红灯留到第二天，或被人 `--no-verify` 绕过 |
| D5 | pre-commit 直接 `exec run.sh`，没有增量、没有提交信息约束 | 仓库变大后变慢 → 人开始绕过；提交无 `Refs` → 反转链断 | 闸门被习惯性绕过；三个月后没人知道某行为什么改 |
| D6 | 人要看懂 AI 的改动，只能读全量 diff | 缺「风险/影响面/该跑什么/该谁拍板」的翻译层 | 人要么全信 AI，要么全不看——两种都翻车 |
| D7 | 失败只留下日志 | 没有把「哪门红 → 候选原因 → 处置顺序」整理成待办 | 下次会话从零开始排查，重复踩坑 |

**关键观察：D1 是根因。** 判定结果是文本，所以 AI 只能"读"，不能"算"；于是所有下游（简报、评审单、分诊、看板、CI）都只能各写一套脆弱的解析。
先把判定变成结构，其余四个接口才成立。

## 2 模型：四环闭环，一个不动点

```text
   ① 开场（brief）        ② 改动（explain）
   4KB 事实卡             风险 / 影响面 / 验证清单
        │                       │
        ▼                       ▼
   人+AI 对齐 ──────────► 编辑与生成
        ▲                       │
        │                       ▼
   ④ 巡检（watch/triage）◄── ③ 闸门（run --json）
   失败→待办单              7 门 + 结构化结果
```

**不动点：唯一事实仍然是代码、数据、基线、`doc/NNN`。**
新增的四个产物（`last_gates.json` / `brief.md` / `review.md` / `TRIAGE.md`）全部是**派生视图**：
由命令生成、可随时重建、不入 git、禁止手改（C08 / C11）。这条守住，闭环就不会长出第二份真相。

三条不可让渡的原则：

1. **判定与措辞分离**：机器认 `id + status`，人读中文。措辞随便改，契约不动。
2. **证据与结论分离**：巡检只准备证据（事实 + 候选原因），结论必须回到 `doc/NNN` 并由人拍板（C09）。
3. **闸门分层，不堆在一步**：秒级进提交、分钟级进推送、小时级进定时（C10）。任何一层超过人的耐心，就会失去那一层。

## 3 Agent 最高开发方法（M01–M12）

这 12 条不是"最佳实践清单"，每条都对应本项目真实翻车过的错误类型，并已经**有机器载体**（没载体的不写进来）。

| # | 方法 | 机制载体 | 防的错误 |
|---|---|---|---|
| M01 | **指令坐标化**：积木号 → 文件:行号 → 字段/单元格 | `BLOCKS.md` + `explain` 的积木归属列 | 「改输出」式模糊指令，来回 3 轮 |
| M02 | **先证据后假设**：遇错先跑命令拿真实报错 | `AI_INSTRUCTIONS` 指挥原则 1 + `run.sh` | AI 猜原因，改错地方 |
| M03 | **一次只改一件事**：一版 1–3 个问题，超 60 行提示拆版 | `explain` 风险规则 | 大改动混在一起，归因不可能 |
| M04 | **双跑对比 + 归因优先**：差异先分类再动手 | 门3 + `TRIAGE` 的「先归因」 | 为对齐错误基线把对的改错 |
| M05 | **约束可执行化**：文字 → 断言 → 钩子（三级进化） | `CONSTRAINTS` → `checks/` → `hooks/` | 约束只靠人记，第二次照犯 |
| M06 | **派生视图不手改**：生成物永远重跑，不补丁 | C02 / C08 / C11 + pre-commit 拦截 | 两份真相，改一份漏一份 |
| M07 | **开场只读 4KB**：状态压缩，规则常驻，历史按需 | `ai.sh brief` → `doc/brief.md` | 跨会话重读 13KB 还漏掉关键 3 行 |
| M08 | **每次改动出评审单**：风险等级 + 约束命中 + 必跑清单 | `ai.sh explain` → `doc/review.md` | 人无法审 AI，只能全信或全不信 |
| M09 | **失败产证据不产结论**：事实 + 候选原因 + 顺序 | `ai.sh triage` → `doc/health/TRIAGE.md` | 自动修复把口径改错 |
| M10 | **无人值守只读**：不自动改代码、不自动重建基线 | `watch_loop.py` 的边界 | 机器替人做业务决定 |
| M11 | **闸门分层**：提交秒级 / 推送全量 / 定时巡检 | 三个 hook + `schedule/setup.sh` | 闸门太慢被 `--no-verify` 绕过 |
| M12 | **改口径同步三处**：模板 + 代码 + 测试断言 | DOD 第 8–11 条人工项 | 显示值与计算值分叉 |

**判断一条方法值不值得留下的唯一标准**：它是否让某个错误**在更便宜的位置被发现**。
写文档是最便宜的一级（人也读、AI 也读），断言次之，钩子再次之，线上最贵。所以顺序永远是：
**事故 → 约束文字 → 断言 → 钩子**，不跳级。反过来（先写复杂钩子再想防什么）必然长出无人维护的资产。

### 反模式（看到就停手）

| 反模式 | 为什么危险 | 替代 |
|---|---|---|
| 「你检查一下有没有问题」 | 没有判据，AI 只能生成乐观报告 | 指向具体门/断言/文件 |
| 用 `grep` 中文输出代替结构化判定 | 措辞一改就静默失效（漏报 > 误报） | `--json` + `id/status` |
| 人工通读全量 diff 当作评审 | 注意力撑不过 300 行，等于没审 | 评审单看风险与约束，diff 只抽样 |
| 自动修复 + 自动提交 | 错误被固化成"标准" | 只出分诊单，人拍板 |
| CI 只跑测试不跑口径 | 测试全绿但业务数错 | 门2/门3 必须进 CI |
| 状态写在聊天/记忆里 | 换会话即失忆 | `STATE.md` + `brief` |

## 4 新增能力与用法

### 4.1 一条命令一条链

```bash
bash tools/ai.sh brief      # ① 开场：4KB 事实卡 → doc/brief.md
bash tools/ai.sh explain    # ② 改动：评审单 → doc/review.md
bash tools/run.sh --out out/ --json   # ③ 闸门：七门 + doc/health/last_gates.json
bash tools/ai.sh triage     # ④ 分诊：FAIL → doc/health/TRIAGE.md
bash tools/ai.sh watch      # ②③④ 的无人值守版（--once 可进 cron/CI）
bash tools/ai.sh gates --out out/     # run.sh --json 的别名
```

### 4.2 每个产物的契约

| 产物 | 生成者 | 消费者 | 契约 | 不入 git |
|---|---|---|---|---|
| `doc/health/last_gates.json` | `run.sh --json` | brief / triage / CI / 看板 | `schema_version=1`，`gates[].id/status` 稳定 | ✓ |
| `doc/brief.md` | `ai.sh brief` | AI 每会话第一读；人接手时 | ≤4KB，「现在/必须知道」必须在最前 | ✓ |
| `doc/review.md` | `ai.sh explain` | 提交前的人 | 风险等级由规则算，不由模型说 | ✓ |
| `doc/health/TRIAGE.md` | `ai.sh triage` | 下次会话的 AI / 值班人 | 只含事实与候选原因，不含结论 | ✓ |
| `doc/health/*.log` | `watch` / launchd | 排障时翻 | 追加写，按日切分 | ✓ |

### 4.3 钩子族

| 钩子 | 时机 | 跑什么 | 耗时 | 为什么在这 |
|---|---|---|---|---|
| `pre-commit` | 每次提交 | 静态四门 + staged 增量密钥 + 生成物拦截 | < 2s | 天天过，必须无感 |
| `commit-msg` | 提交信息落定 | 类型/摘要格式 + `Refs: doc/NNN` | < 50ms | 反转链在提交时最便宜 |
| `pre-push` | 每次推送 | 七门（带 `--out`）+ `tests/run_all.sh` | 分钟级 | 一次推送一次，等得起 |
| `schedule --watch` | 每 N 秒（批处理） | `ai.sh watch --once` | 秒级 | 机器等，人不等人 |

逃生阀只有一个：`git commit --no-verify`。用了要在迭代文档写明原因——**允许例外，不允许无记录例外。**

## 5 防错机理：为什么这套比"更努力地 review"可靠

1. **把记忆负担转成结构负担**：约束不再靠"记得"，靠 `brief` 每会话出现在眼前第一条。
2. **把判断转成比较**：`explain` 不给结论，只给"风险等级 + 命中约束 + 必跑清单"，人做的是确认而非推理。
3. **把信任转成可审计**：每次失败都有 `TRIAGE` + 日志 + 命令，谁都能复现，不必相信任何人的描述。
4. **把"发现错误"提前**：编辑期（watch）→ 提交（pre-commit）→ 推送（pre-push）→ 定时（launchd），四道都失败才会流到线上。
5. **把 AI 的自由度收在可回滚的范围内**：AI 可以改代码，但不能改基线、不能改生成物、不能跳过闸门、不能替人定口径。

### 可测的健康度（每 5 版手算一次，写进迭代文档）

| 指标 | 怎么算 | 目标 |
|---|---|---|
| 早发现率 | 失败在 pre-commit 及之前拦下的次数 / 总失败次数 | ↑ |
| 绕过率 | `--no-verify` 次数 / 提交次数 | < 5% |
| 交接完整率 | 有 `Refs: doc/NNN` 的提交 / 总提交 | ≥ 95% |
| 上下文开销 | `context_budget.py` 的入口合计 + brief 字节 | 入口 ≤ 24KB，brief ≤ 4KB |
| 状态真实率 | `STATE.md` 声称"能跑"且 `run.sh` 全绿的抽查次数 / 抽查总数 | 100% |
| 资产活性 | `STATE.md` 活跃度表里"连续 5 版未发挥作用"的条目数 | 0 |

## 6 落地与迁移

### 6.1 新项目

```bash
bash tools/init.sh ~/path/新项目 --tier=L1     # 已含 v3 全部工具与三个钩子
```

### 6.2 已有项目（增量迁移，不动业务代码）

```bash
# 1) 拷工具与新钩子
rsync -a 模板/tools/ 项目/tools/
git -C 项目 config core.hooksPath tools/hooks
# 2) .gitignore 追加派生视图
printf 'doc/brief.md\ndoc/review.md\ndoc/health/\n' >> 项目/.gitignore
# 3) 入口文件加一行「开工先 brief」（否则新工具没人用）
#    在 AGENTS.md 的必读清单前加：bash tools/ai.sh brief
# 4) 第一次跑通
cd 项目 && bash tools/run.sh --json && bash tools/ai.sh brief
```

**不要**一次性把旧项目的 `AI_INSTRUCTIONS` 全换掉——先跑 `brief` 与 `explain`，让团队感到"少读了东西还更清楚"，
再逐步把约束迁到 `CONSTRAINTS.md`。工具的采纳率比工具的完备度重要。

### 6.3 分档

| 档 | 带什么 | 什么时候够 |
|---|---|---|
| L0 | 仅 AGENTS/AI_INSTRUCTIONS/STATE | 一次性脚本、<100 行 |
| L1 | + 七门 + `ai.sh`（brief/explain/triage）+ 三钩子 | 绝大多数项目（默认） |
| L2 | + `schedule/`（每日体检或每 5 分钟巡检） | 服务化、多人、>3 个月 |

## 7 验收（模板自测覆盖）

`bash tools/selftest.sh` 在临时项目里断言以下新能力，失败即视为防线回归：

1. `run.sh --json` 产出合法 JSON，`schema_version / gates[].id / overall` 齐全，且 FAIL 时 `overall=FAIL`。
2. `ai.sh brief` 产出 ≤4KB，且包含「现在」「必须知道」「复跑命令」三段。
3. `ai.sh explain` 在注入一处 `except: pass` 后把风险判为 `HIGH` 并列出命中反模式。
4. `ai.sh triage` 在 FAIL 时生成 `TRIAGE.md` 且含「候选原因」「处置顺序」；全绿时移除过期分诊单。
5. `commit-msg` 拒绝无 `Refs` 的提交信息、接受合规格式。
6. `pre-commit` 拒绝把 `doc/review.md` 等生成物入库。
7. `secret_scan --files` 只扫指定文件（增量路径可用）。

## 9 反转与债务

- **反转 R-v3-1**：v2.6 的 pre-commit「直接 exec run.sh」被 v3.0 反转——改为快检 + 增量密钥 + 生成物拦截，全量下沉 pre-push。
  理由：`README` 要求"秒级"，实现却是全量七门；仓库一大，人一定会绕过。
- **反转 R-v3-2**：v2.6「巡检=每日一次」被 v3.0 扩展为「每日体检 / 每 N 秒 watch」两模式，仍然坚持批处理、不做常驻守护。
- **顺手修的既有缺陷**：`schedule/setup.sh` 生成的 launchd plist 里 `&&` 未做 XML 转义，`launchctl load` 会报
  `unknown ampersand-escape sequence`，而安装脚本仍然打印"已安装"——定时任务静默不生效。
  v3.0 转义 `&` / `<`，并在 selftest 里加 `plutil -lint` 断言（有 `plutil` 才跑）。
  **这条最值得记：无人值守系统最危险的失败不是报错，是"看起来装上了"。**
- **债务 D11**：`explain.py` 的积木归属靠 `BLOCKS.md` 的文件列精确匹配；文件改名未同步时只会显示"未登记"，不会报错。→ 候选修法：门4 增加「BLOCKS 文件列必须存在且被至少一次引用」的强校验。
- **债务 D12**：`brief.py` 的 STATE 解析依赖 `- **键**：值` 格式；若某人改写为表格会静默丢失。→ 候选修法：解析失败时在简报里显式打印「STATE 解析失败」而不是留空。
- **债务 D13**：`TRIAGE` 的候选原因表是静态映射（7 门）；新增门必须同步 `REMEDY`，否则显示"未登记的门"。→ 候选修法：未登记时直接 FAIL 自测。
- **债务 D14**：`pre-commit` 同时跑「全仓门6」与「staged 增量扫描」，属有意冗余；仓库文件数超过约 2000 时全仓扫描会突破 2 秒预算。→ 候选修法：`run.sh` 增加 `--only=staged`，把门6 的体积扫描下沉 pre-push（需同步 C10）。

## 10 一句话结论

**Agent 开发的天花板不是模型能力，而是「约束被执行的确定性」。**
把判定变成结构（JSON）、把状态压成简报（4KB）、把改动翻成评审单、把失败整理成分诊单、把闸门按人的耐心分层——
五件事做完，AI 的产出就从"需要人盯着"变成"可以被人抽查"。
